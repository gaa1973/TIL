# バックエンド (auth-api) の役割分担

バックエンドは、機能ごとに責任を分担する「レイヤー化アーキテクチャ」という、非常にクリーンな構造になっています。これは、よく組織された会社のようなものです。

## src/routes/ (交通整理係)

auth.ts, memos.ts: API の入り口です。彼らの唯一の仕事は、やってきた URL リクエスト（例: POST /api/auth/login）を、担当部署（コントローラー）に振り分けることです。リクエストをどう処理するかは知らず、ただ担当者に渡すだけの役割です。

## src/controllers/ (受付係)

auth.controller.ts, memos.controller.ts: 受付係として、HTTP リクエスト (req) とレスポンス (res) を直接扱います。主な責務は以下の通りです。
リクエストからデータを取り出す（例: req.body）。
実際の仕事を行う「マネージャー」（サービス）を呼び出す。
サービスから受け取った結果を、クライアント向けの HTTP レスポンス（res.json(...) など）に整形して返す。 Web の世界（HTTP）と、アプリケーション内部のロジックを繋ぐ「橋渡し役」です。

## src/services/ (頭脳・マネージャー)

auth.service.ts, memos.service.ts: アプリケーションの核となるビジネスロジック（頭脳）です。例えば、「ユーザーを登録する」という仕事なら、ユーザーが既に存在しないか確認し、パスワードをハッシュ化し、データベース係にユーザー作成を依頼する、といった一連の流れを組み立てます。HTTP のことは何も知りません。

## src/models/ (データベース係)

user.ts, memos.ts: この層の唯一の責任は、Prisma を使ってデータベースと直接やり取りすることです。findUnique（探す）、create（作る）、delete（消す）といった、単純で単一目的の命令を実行します。なぜユーザーを作るのかは知らず、ただ「どうやって作るか」だけを知っています。

## その他の重要なファイル

src/app.ts: バックエンドアプリケーション全体を組み立てるメインファイルです。すべてのミドルウェア（cors など）やルーターをここで結合します。
tsconfig.json: TypeScript コンパイラの設定ファイルです。コードをどのようにコンパイルするかを指示し、@/\* のようなパスエイリアスを定義して import 文を綺麗に保ちます。

# フロントエンド (my-login-app) の役割分担

フロントエンドも、再利用可能な部品（コンポーネント）を組み合わせる、クリーンな設計になっています。

## src/hooks/ (専門道具)

useApi.ts: これは「カスタムフック」と呼ばれる、再利用可能なロジックの部品です。API 通信を行う際の定型的な処理（ローディング状態の管理、エラーハンドリング、取得したデータの保持）をすべて引き受けます。このフックを使うことで、UI コンポーネントは複雑な fetch のロジックを持つ必要がなくなります。

## src/components/ (UI の部品)

LoginForm.tsx, MemoApp.tsx: これらは UI コンポーネントです。主な仕事は、ユーザーに見える画面（UI）を描画し、ユーザーの操作（ボタンクリックや文字入力）に対応することです。useState や自作の useApi のようなフックを使って、自身の状態を管理し、必要な処理を実行します。

## src/App.tsx (司令塔・組み立て係)

アプリケーション全体のコンテナ（入れ物）となるコンポーネントです。主な役割は、アプリケーション全体のグローバルな状態（例: isLoggedIn）を管理し、その状態に応じてどの主要コンポーネント（LoginForm か MemoApp）を表示するかを決定することです。UI 部品をどう配置するかを指揮する「司令塔」の役割を果たします。
このようにコードを分離することで、アプリケーションの特定の部分を見つけ、修正し、機能追加することが、他の部分を壊すことなく非常に簡単になります。これが、スケール可能でメンテナンスしやすいソフトウェアの基本です。

# MemoApp.tsx の変更点

変更点の解説
apiFetch の削除: コンポーネント内にあった apiFetch 関数を削除し、代わりに useApi フックをインポートしました。
useApi の複数インスタンス化:
メモの取得（GET）、作成（POST）、削除（DELETE）という異なる操作のために、useApi フックを 3 回呼び出しています。
これにより、各操作のローディング状態（isLoadingMemos, isCreating, isDeleting）を個別に管理でき、例えば「作成中に削除ボタンは押せる」といった、より良いユーザー体験を実現できます。
useEffect の役割変更:
最初の useEffect は、コンポーネントがマウントされた時に一度だけ fetchMemos を呼び出す役割に専念します。
新しく追加した 2 つ目の useEffect は、useApi フックから取得した fetchedMemos データが更新されたのを監視し、コンポーネントの memos 状態に反映させます。
イベントハンドラの修正:
handleCreateMemo と handleDeleteMemo は、useApi から取得した createMemoRequest と deleteMemoRequest を呼び出すように変更されました。
API 呼び出しが成功したら、fetchMemos を再度呼び出して、画面のメモ一覧を最新の状態に更新しています。
try...catch を使って、API 通信で発生したエラーを捕まえ、setMessage を使ってユーザーに通知します。
ローディング表示の強化:
メモ一覧の読み込み中は「読み込み中...」と表示します。
メモ作成中は「作成」ボタンを無効化し、テキストを「作成中...」に変更します。
このリファクタリングにより、MemoApp コンポーネントも責務が明確になり、より堅牢で再利用性の高いコードになりました。

# 🔑 ジェネリクス型の目的と仕組み

## 1. 目的：「型を抽象化し、再利用性を高める」

ジェネリクス（Generics）は、「処理の内容は同じだが、扱うデータの型だけが変わる関数やクラス」を作成するために使用されます。

問題: ユーザーの配列を返す関数、メモの配列を返す関数、それぞれ別の型が必要です。

ジェネリクスでの解決: 関数を定義する際に「T」（Type の頭文字）のような仮の型を使い、その関数が呼び出される時点で、その仮の型を具体的な型（User[] や Memo[]）に置き換えます。

## 2. 仕組み：「T」という型変数

ジェネリクスの構文は、山括弧 < > を使い、その中に型を表す仮の変数（慣習として T, K, V などが使われます）を記述します。

TypeScript

// T: ジェネリックな型変数
function identity<T>(value: T): T {
return value;
}
この T は、**「この関数が呼び出されるまで、何型になるか分からない箱」**だとイメージしてください。

# 💡 具体的な使用例（React と API）

ジェネリクスがなぜ便利かを、データ取得の関数を例に見てみましょう。

例 A: ジェネリクス不使用（非効率）
ユーザーデータを取得する関数と、メモデータを取得する関数を、別々に定義する必要があります。

TypeScript

// ユーザーの配列を返す
function fetchUsers(): User[] { /_ ... _/ }

// メモの配列を返す
function fetchMemos(): Memo[] { /_ ... _/ }
例 B: ジェネリクス使用（再利用可能）
API 通信のロジック（fetch やエラー処理）は全て同じなので、ジェネリクスを使って一つの関数にまとめることができます。

TypeScript

// fetcher が返す型を T という型変数で定義
async function fetcher<T>(url: string): Promise<T> {
const res = await fetch(url);
if (!res.ok) throw new Error("Failed to fetch");
return res.json() as T; // 戻り値の型を T として保証
}

// 呼び出し時：具体的な型を指定する
// ユーザーデータの取得
const users = await fetcher<User[]>('/api/users');
// ⬅︎ T が User[] に置き換わる

// メモデータの取得
const memos = await fetcher<Memo[]>('/api/memos');
// ⬅︎ T が Memo[] に置き換わる
結論: fetcher 関数の中身は一つですが、ジェネリクスを使うことで、**「ユーザーの配列を返す関数」としても、「メモの配列を返す関数」**としても、安全に再利用できるようになるのです。

この仕組みを理解できると、TypeScript を使ったリファクタリングが格段に進み、コードの品質が高まります。

## まとめ

コードの共通化すると、型の安全性が弱まる。
型の安全性を高めると、コードの共通化が難しくなる。
ジェネリクスは、コードの共通化と型の安全性を両立するための言語機能。
ジェネリクスは、型も引数のように扱うという発想。

# カスタムフック

const { request: createMemoRequest, isLoading: isCreating } = useApi<Memo>();

このコードは、右側から左側に向かって読むと理解がスムーズです。

## 1. 右側: useApi<Memo>()

これは、私たちが作ったカスタムフック useApi を呼び出しています。
useApi は、API 通信に必要な道具一式（データ、ローディング状態、エラー情報、リクエスト関数）が入った「道具箱」を返す工場のようなものです。
<Memo> の部分はジェネリクスで、「この道具箱で扱うデータは Memo 型ですよ」と、データの種類を教えてあげています。
この useApi<Memo>() を呼び出すと、内部的には以下のようなオブジェクトが返ってきます。

javascript
Show full code block
{
data: null, // API から取得したデータ（最初は空）
error: null, // エラーメッセージ（最初は空）
isLoading: false, // 通信中かどうかの状態（最初は false）
request: (/_ ... _/) => { /_ ... _/ } // API リクエストを実行する関数
}

## 2. 左側: const { request: createMemoRequest, isLoading: isCreating } = ...

これは JavaScript の分割代入 (Destructuring Assignment) という機能です。右側のオブジェクトから、必要なプロパティだけを抜き出して、新しい定数として定義します。
request: createMemoRequest:
これは分割代入の応用で、プロパティの名前を変更しています。
「道具箱オブジェクトから request という名前のプロパティ（関数）を取り出し、createMemoRequest という新しい名前の定数として定義してください」という意味です。
isLoading: isCreating:
同様に、「道具箱オブジェクトから isLoading という名前のプロパティ（状態）を取り出し、isCreating という新しい名前の定数として定義してください」という意味です。
なぜ名前を変更するのか？
MemoApp.tsx の中では、useApi フックを 3 回呼び出して、それぞれ「一覧取得」「作成」「削除」という異なる仕事を担当させています。

typescriptreact
Show full code block
// メモ一覧取得の専門家
const { ..., request: fetchMemos, isLoading: isLoadingMemos } = useApi<Memo[]>();
// メモ作成の専門家
const { ..., request: createMemoRequest, isLoading: isCreating } = useApi<Memo>();
// メモ削除の専門家
const { ..., request: deleteMemoRequest, isLoading: isDeleting } = useApi<void>();
もし名前を変更しないと、すべての request 関数と isLoading 状態が同じ名前になってしまい、どの処理のローディング状態なのか区別がつかなくなってしまいます。

createMemoRequest や isCreating のように、それぞれの役割に合った分かりやすい名前を付けることで、コードが非常に読みやすくなり、バグも発生しにくくなるのです。

# useApi フックの目的

このフックの目的は、API 通信に伴う面倒な定型処理をすべて一つの場所にカプセル化（閉じ込める）することです。具体的には、以下の処理を引き受けてくれます。

通信中の「ローディング状態」の管理
通信成功時の「データ」の保持
通信失敗時の「エラー情報」の保持
これにより、各 UI コンポーネント（LoginForm や MemoApp）は、これらの複雑な状態管理を自分で行う必要がなくなり、UI の表示に専念できます。

ソースコードの詳細解説
typescript
Show full code block
import { useState, useCallback } from "react";

const API_BASE_URL = "http://localhost:8000/api";

/\*\*

- API 通信をカプセル化し、データ、ローディング状態、エラーを管理する汎用カスタムフック
- @template T 期待されるデータの型
- @returns { data, error, isLoading, request }
  \*/
  export const useApi = <T>() => { // 1. ジェネリクス<T>
  // 2. ３つの状態を管理
  const [data, setData] = useState<T | null>(null);
  const [error, setError] = useState<string | null>(null);
  const [isLoading, setIsLoading] = useState<boolean>(false);

// 3. API リクエストを実行する関数
const request = useCallback(
async (endpoint: string, options: RequestInit = {}) => {
// 4. 通信開始の準備
setIsLoading(true);
setError(null);

      // 5. try...catch...finally で安全に通信
      try {
        const res = await fetch(`${API_BASE_URL}${endpoint}`, {
          credentials: "include", // Cookieを送受信するために必須
          ...options,
          headers: {
            "Content-Type": "application/json",
            ...options.headers,
          },
        });

        // 6. レスポンスボディの処理
        const responseData =
          res.status === 204 ? { success: true } : await res.json();

        // 7. エラーレスポンスの処理
        if (!res.ok) {
          throw new Error(responseData.message || "API request failed");
        }

        // 8. 成功レスポンスの処理
        setData(responseData as T);
        return responseData as T;

      } catch (err: any) {
        // 9. 通信失敗時のエラー処理
        console.error("API Hook Error:", err);
        setError(err.message || "予期せぬエラーが発生しました。");
        throw err; // 呼び出し元でさらに処理できるようエラーを再スロー

      } finally {
        // 10. 通信終了の処理
        setIsLoading(false);
      }
    },
    [] // 11. useCallback の依存配列

);

// 12. 外部で使えるように状態と関数を返す
return { data, error, isLoading, request };
};
ジェネリクス <T>: このフックを「どんな型のデータでも扱える」ようにするための型引数です。useApi<Memo[]>() のように呼び出すことで、data の型が Memo[] であることを TypeScript に教え、型安全性を保証します。

## 3 つの状態管理:

data: API から正常に取得したデータを保持します。
error: エラーが発生した場合に、そのメッセージを保持します。
isLoading: API との通信中であるかを示すフラグです (true なら通信中)。
request 関数: このフックの本体です。実際に API リクエストを実行します。useCallback で囲むことで、この関数が不必要に再生成されるのを防ぎ、パフォーマンスを最適化しています。

通信開始の準備: リクエストが始まる直前に、isLoading を true にし、前回のエラー情報 error をリセットします。

try...catch...finally: 非同期処理である fetch は失敗する可能性があるため、この構文で囲むことで、エラーが発生してもアプリケーション全体がクラッシュするのを防ぎます。

レスポンスボディの処理: DELETE 成功時などに返される 204 No Content はボディが空なので、res.json() を呼ぶとエラーになります。それを防ぐために、ステータスコードをチェックして条件分岐しています。

エラーレスポンスの処理: サーバーがエラー（400 番台や 500 番台）を返した場合、res.ok は false になります。その場合、レスポンスボディに含まれるエラーメッセージを使って Error オブジェクトを生成し、throw します。これにより、処理は catch ブロックにジャンプします。

成功レスポンスの処理: 通信が成功した場合、取得したデータを data 状態に保存し、呼び出し元にもそのデータを返します。

通信失敗時のエラー処理: ネットワーク接続がない場合や、throw されたエラーをここで捕まえます。エラー内容をコンソールに出力し、UI に表示するための error 状態を更新します。最後に throw err でエラーを再スローすることで、呼び出し元のコンポーネント側でも catch できるようにしています。

通信終了の処理: finally ブロックは、成功しようが失敗しようが必ず最後に実行されます。ここで isLoading を false に戻し、ローディング状態を確実に終了させます。

useCallback の依存配列: 空の配列 [] を指定することで、この request 関数はコンポーネントが最初にレンダリングされた時に一度だけ生成され、その後は再利用されることが保証されます。

返り値: このフックが管理する 3 つの状態 (data, error, isLoading) と、API を呼び出すための request 関数をオブジェクトとして返すことで、コンポーネント側でこれらを自由に利用できるようになります。
